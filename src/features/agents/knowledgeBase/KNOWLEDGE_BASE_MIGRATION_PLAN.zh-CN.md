# 知识库主体功能迁移计划与问题台账

## 1. 文档目的

本文用于持续记录知识库主体功能从参照前端项目迁移到本项目的范围、阶段、完成标准、接口依赖和联调问题。

迁移过程中以参照前端项目的业务字段、接口契约和交互语义为功能依据；页面结构、视觉样式、状态反馈和基础组件统一使用本项目现有体系，不直接复制参照项目的 UI 实现。

## 2. 本次迁移边界

### 2.1 必须迁移

| 主体能力 | 迁移内容 | 完成目标 |
| --- | --- | --- |
| 知识库管理 | 列表、搜索、分页、新建、编辑、删除、基础配置、状态与统计展示 | 知识库可完成真实维护，刷新后数据一致 |
| 文件上传、解析、预览 | 文件上传、文件列表、解析进度、失败原因、停止、重试、启停、下载、删除和多类型预览 | 文件从上传到可检索形成可观察闭环 |
| 检索测试 | 检索问题、必要检索参数、召回结果、相似度、文档来源和分页 | 能使用当前知识库真实验证召回效果 |
| 引擎设置 | 当前租户的 Embedding、Parser、Rerank、LLM、VLM、OCR 默认模型绑定 | 解析、索引和检索所依赖的模型可真实配置，不再只显示后端报错 |

分块数据是文件解析和检索结果之间的必要中间产物，因此分块查看、编辑、删除和启停属于文件解析闭环的一部分，不作为额外扩展功能处理。

### 2.2 暂不迁移

- 知识库开放 API 文档。
- API Key 创建、启停和删除。
- 独立 RAGFlow 知识库管理页面。
- RAGFlow 服务健康检查、GraphRAG/RAPTOR 跟踪等运维能力。
- 分类树的新增、编辑、删除等扩展管理能力。
- 与本次三条主体链路无关的高级元数据管理。

上述文件和路由不要求删除，只是不进入本轮入口、开发与验收范围。

## 3. 实现原则

1. **参照功能，不复制外壳**：参照项目决定业务功能、字段和交互语义；本项目使用 `src/components/ui`、Tailwind 语义颜色和现有明暗主题。
2. **真实接口替换 Mock**：不得用前端随机进度、内存数组或固定召回数据标记功能完成。
3. **按领域拆分**：知识库、文档、分块、检索分别建立类型、API 和查询逻辑，避免继续扩大单页组件。
4. **异步任务可观察**：解析必须明确展示排队、解析、分块、向量化、完成、失败和取消状态；轮询必须有停止条件。
5. **保存与刷新一致**：创建、修改、启停、解析和删除完成后，重新加载页面必须得到一致结果。
6. **前后端边界明确**：参照前端已有但当前后端未实现的能力保留前端契约并登记问题，不通过假数据掩盖，也不自行修改后端业务。
7. **不兼容参照项目错误旧数据**：只接受本项目迁移后定义的有效数据与接口响应，不为无效历史数据放松校验。

## 4. 目标目录划分

现有页面目录继续保留，逐步调整为以下结构：

```text
src/features/agents/knowledgeBase/
├── api/
│   ├── datasetApi.ts       # 知识库维护与统计
│   ├── documentApi.ts      # 上传、解析、进度、下载与删除
│   ├── chunkApi.ts         # 分块查询与维护
│   ├── retrievalApi.ts     # 召回测试
│   └── modelConfigApi.ts   # 租户级知识引擎模型绑定
├── components/
│   ├── dataset/            # 知识库列表与配置
│   ├── document/           # 文件列表、进度和操作
│   ├── preview/            # PDF、Word、Excel、文本和图片预览
│   ├── chunk/              # 分块查看与维护
│   └── retrieval/          # 检索表单和召回结果
├── hooks/                  # 查询、变更、轮询和缓存刷新
├── types.ts                # 领域类型与接口契约
├── utils/                  # 状态、格式与响应映射
├── KnowledgeBasePage.tsx   # 页面编排，不承载底层协议细节
└── KNOWLEDGE_BASE_MIGRATION_PLAN.zh-CN.md
```

目标划分与参照项目的 `dataset / document / chunk / retrieval` 领域边界一致，但不复制其样式类名和大型单文件结构。

状态约定：`未开始`、`进行中`、`前端完成待联调`、`受后端阻塞`、`已完成`。

## 8. 问题登记格式

后续遇到问题时直接追加到第 7 节，不另建零散说明。每条至少记录：

- 问题编号与发现日期。
- 所属阶段和复现入口。
- 参照前端的请求及预期表现。
- 当前后端的实际响应或错误。
- 判断属于前端缺口、接口差异、环境数据缺失还是后端未实现。
- 临时处理、最终处理及验收结果。

不得仅记录“不可用”或“接口有问题”，也不得用前端假数据将问题标记为完成。
